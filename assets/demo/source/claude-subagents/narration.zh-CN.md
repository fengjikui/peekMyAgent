# 《子 Agent 在哪里运行，结果怎样回来》中文旁白母稿

本稿是 Claude Code 机制系列第三章的中文事实母稿。故事、画面、字幕和后续配音都以这份事实为准；音色选择另行处理，不阻塞内容生产。

- 总时长草案：约 04:14
- 画面：中文 Viewer、Claude 主题、2048×1056 原始帧
- 真实环境：Claude Code 2.1.220 + PMA + 本地确定性 Anthropic 假上游
- 任务：启动两个只读 Explore 子 Agent；一个读取快速开始，一个列出公开文档；父 Agent 等齐后汇总
- 证据边界：Claude Code 的启动、子分支、工具执行和异步通知来自真实 CLI；模型回复由本地假上游固定生成，不代表远端 Claude 的回答质量
- 术语：Agent、Explore、`tool_use`、`tool_result`、`task-notification`、Read、Bash、Message、Raw 保留原写法

## 教学合同

观众看完后应该能复述：

> 父模型先返回两个 `Agent` tool use，Claude Code 再启动两个独立子分支。每个子 Agent 仍会经历自己的模型请求、工具调用和工具结果。父级先收到后台启动确认；分支完成后，Claude Code 再用系统生成的 `task-notification` 把结果送进父级后续请求。父 Agent 可以等待两次异步通知，在结果齐备后汇总。PMA 用 Turn、Request 和多 Agent 看板把这条链连起来。

本章不把普通子 Agent 说成 Agent Team，不声称它们彼此直接通信，也不把本地假上游的固定回复描述成远端模型能力。本例由用户明确要求两个子 Agent，因此验证的是启动、分支、异步完成和回流，不证明模型自主选择了并行策略。

## 00:00–00:15　子 Agent 不是一个黑盒名字

画面：标题卡显示“父级发起、分支执行、异步完成、父级汇总”四步预告。

旁白：

Claude Code 说它启动了两个子 Agent。它们真的各自做了什么？哪个先完成？结果怎样回到父对话？这一支视频，我们用一条真实 CLI 轨迹，把父级、分支和异步回流逐段打开。

## 00:15–00:37　先看完整路径

画面：完整三栏时间线。编号 1 先聚焦左侧会话中的 8 请求总数；讲完请求规模后与编号 2 交叉淡出，编号 2 聚焦 Turn 1 顶部的机制流程。

旁白：

任务没有业务门槛：一个分支读取快速开始，另一个分支列出公开文档，最后给三条建议。真实 Claude Code 一共产生八次模型请求；PMA 把它们整理成三个 Turn。Turn 定位用户阶段，Request 继续查看阶段内部的模型往返。

## 00:37–01:01　谁发起了两个分支？

画面：父请求一的两个 `Agent` 调用。编号 1 标记中栏点击来源，随后与编号 2 交叉淡出；编号 2 聚焦右栏两组 `tool_use` 参数。

旁白：

父请求一的回复里有两个 Agent tool use。每项都有独立调用标识、任务描述、完整 prompt 和 Explore 类型。模型返回的是结构化委派请求；真正创建后台任务、处理权限并运行子 Agent 的，是 Claude Code。

## 01:01–01:23　两级导航怎样容纳两条分支？

画面：短点击波纹落在 `multi-agent · 2 个子 Agent` 的展开控件并自动消失；编号 1 随后标记“核对快速开始”，讲解完成后与编号 2 交叉淡出，编号 2 接管“核对公开目录”。

旁白：

展开 multi-agent，看板里出现“核对快速开始”和“核对公开目录”两个分支。它们各自有两次模型请求。PMA 没把子 Agent 压成一句摘要，而是保留分支名、类型、请求数量以及各自的内部时间线。

## 01:23–01:43　快速开始分支先调用 Read

画面：选择“核对快速开始”，点击 Request 2 的 Read。编号 1 标中栏调用来源，随后淡出；编号 2 聚焦右栏的工具名和公开临时文件路径。

旁白：

进入第一个分支，请求二先收到只读任务，再返回 Read 调用，目标是公开演示目录里的 docs/guide.md。子 Agent 不是一个只能返回结论的黑盒；只要请求被捕获，它选择的工具和参数都能继续检查。

## 01:43–02:03　工具结果先回到子分支

画面：Request 5 的 Read 结果。编号 1 标记结果行与“来源 #2”，随后与编号 2 交叉淡出；编号 2 聚焦右栏 `user/tool_result` 的公开文档内容。

旁白：

同一分支后来的请求五收到匹配的 Read tool result。中栏“来源二”可以跳回原始调用，右栏则保留用户角色的结果内容。这个结果先供子 Agent 形成分支小结，还不是父 Agent 的最终回答。

## 02:03–02:25　另一个分支有独立工具闭环

画面：切换“核对公开目录”。编号 1 先聚焦 Request 3 的 Bash 调用；讲完后渐隐，编号 2 聚焦 Request 6 的 Bash 结果和两条目录结论。

旁白：

第二个分支没有共享第一条分支的 Read 历史。它在请求三调用 Bash，运行一条只读 `find` 命令；请求六收到 `docs/guide.md` 与 `docs/viewer.md`，再给出自己的两条建议。PMA 把两个分支分栏呈现，避免同名工具和相邻请求在长会话里混到一起。

## 02:25–02:53　后台启动确认，不等于任务已经完成

画面：父请求四和右栏等待回复。编号 1 聚焦中栏的两条 Agent 工具结果；随后淡出，编号 2 聚焦右栏“后台启动，等待完成通知”。

旁白：

这里要区分两个事件。Request 四收到的两个 Agent tool result 只是“后台任务已启动”的确认，不等于子任务内容已经完成。父级回复也明确说：等待完成通知，不提前猜测结果。真正的分支结论要等后续 task-notification。

本章不公开原始任务 ID 和输出文件路径。脱敏后的完成事件结构是：

```xml
<task-notification>
  <tool-use-id>agent_quickstart</tool-use-id>
  <status>completed</status>
  <result>公开的子任务结论</result>
</task-notification>
```

它是系统生成的后台任务事件，不是用户又发了一条消息。

## 02:53–03:17　第一个完成通知到达，父级继续等待

画面：Turn 2 的系统通知摘要和父级等待回复。编号 1 先聚焦 `[SYSTEM NOTIFICATION - NOT USER INPUT]`；讲完后与编号 2 交叉淡出，编号 2 聚焦“第一个已经返回，另一个仍在运行”。

旁白：

目录分支先完成。Claude Code 把第一个 task-notification 放进父级 Request 七，PMA 因而显示 Turn 二。顶部明确标出这不是用户输入；父级回复则说明另一个分支仍在运行，所以它继续等待，没有提前汇总。

## 03:17–03:39　第二个完成通知怎样进入下一轮？

画面：Turn 2 与 Turn 3 同时可见。编号 1 标记第一个完成通知和等待回复；编号 1 保留并降为次要，编号 2 再标记 Turn 3 的第二个通知和最终回答，用于建立先后关系。

旁白：

快速开始分支随后完成。第二个 task-notification 进入 Request 八，PMA 显示 Turn 三。现在两级导航的价值就清楚了：三个 Turn 表示启动、第一次完成、第二次完成；八个 Request 继续保留父级和两个子分支的内部往返。

## 03:39–03:59　最终回答真的使用了两个结果吗？

画面：Request 8 的 Response。短点击波纹落在中栏最终“详情”入口并自动消失；证据编号 1 随后聚焦右栏三条最终结论。

旁白：

打开 Request 八的 Response，三条结论分别引用快速开始分支和目录分支，还说明两个结果都回到了父对话。现在我们不仅知道“启动过子 Agent”，还可以核对每个分支做了什么、何时完成，以及父级是否真正使用了结果。

## 03:59–04:14　四步记忆点

画面：结束卡显示“父级发起、分支工具闭环、完成通知、父级汇总”四步记忆点。

旁白：

记住四步：父级发起 Agent 调用；子分支完成自己的工具闭环；完成通知异步回到父级；父 Agent 等齐后汇总。PMA 的价值，是把这四步放进一条可以逐项核对的证据链。

## 官方事实与本章边界

- Claude Code 当前工具参考把 `Agent` 描述为启动子 Agent 处理复杂、多步任务的工具；旧版本和旧资料中可能仍出现 `Task` 名称：<https://code.claude.com/docs/en/tools-reference>
- 官方子 Agent 文档说明，每个子 Agent 在自己的上下文中工作，并把结果返回主对话；普通子 Agent 与允许成员直接通信的 Agent Team 不同：<https://code.claude.com/docs/en/sub-agents>
- 当前文档说明普通子 Agent 不能继续生成自己的子 Agent；本章不演示嵌套委派，也不把它写成已支持能力。
- 本次真实 CLI 轨迹确实表现为两个后台任务和先后完成；它证明异步启动与错峰回流，不用于宣称性能加速比例。
- 本地确定性上游只控制固定模型回复。Claude Code 的请求形态、工具生命周期、子 Agent 头、完成通知和 Viewer 解析来自真实运行。

## 文档制作中发现的产品反馈

当前 Viewer 的“父级启动与回流证据”会把 Request 4 中的 Agent 启动确认 `tool_result` 标成回流位置；但这条真实异步轨迹的任务完成事件实际分别出现在 Request 7 和 Request 8 的 `task-notification`。本章因此不把现有“已回流”标签单独当作完成证明，而是组合使用启动等待回复、两次系统通知和最终 Response。这个差异作为产品反馈交给功能迭代任务，本分支不修改运行时代码。

## 公开与脱敏规则

- 可以公开：虚构项目名、公开测试文档、Read / Bash 参数、固定模型回复、3 Turn / 8 Request 总览；
- 不公开：任务 ID、Agent ID、输出文件路径、请求 Header、原始日志、真实用户配置；
- 原生通知需要展示时，使用上面的脱敏 XML；不得发布含内部 ID 和本地输出路径的 Message / Raw 截图；
- 每张画面同时检查 2048×1056 原图、1920×1080 故事板和 1024×576 缩略预览。
