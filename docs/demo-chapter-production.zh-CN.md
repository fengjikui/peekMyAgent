# 中文文档与演示的章节生产线

本文把“写文档、采集素材、制作视频”收束为同一条可重复生产线。每个章节只回答一个用户问题，并以当前产品中的真实证据完成闭环；音色选择与 TTS 调优另行处理，不阻塞故事、画面和字幕母稿。

## 长期目标

面向三类观众持续制作中文优先的内容：

| 观众 | 第一问题 | 章节必须给出的答案 |
| --- | --- | --- |
| 第一次接触 PMA 的 Harness 用户 | “它比终端和普通日志多告诉我什么？” | 一条无需业务背景的完整证据链，以及安装、启动、观察、停止和清理的最短路径 |
| 想理解 Claude Code、Codex 等 Harness 的开发者 | “用户、Harness 和远端模型怎样往返？” | System、工具定义、模型参数、工具调用、结果、子 Agent 和上下文变化分别出现在何处 |
| 正在开发自有 Agent / Harness 的开发者 | “我的封装和关联是否正确？” | OpenAI / Anthropic 原生协议、call id、角色顺序、Raw、来源关联与异常排查方法 |

内容顺序始终先回答“为什么值得看”，再解释“它怎样实现”。README 只承担首页和快速开始；完整机制进入任务式用户手册和独立视频。

## 一章的固定产物

每章使用同一组可替换、可复核的产物：

1. **教学合同**：目标观众、单一问题、学完后能复述的结论、明确不讲什么；manifest 保存内容边界，catalog 另保存可由脚本核对的开场、价值、证据与收束镜头。
2. **非敏感场景**：公开测试项目、确定性假上游、输入、预期工具与模型回复、隐私边界。
3. **事实核对**：当前仓库、真实 Viewer 和必要的 Harness 官方文档；合成轨迹与真实 CLI 证据分开标注。
4. **故事线**：疑问钩子、最短任务、PMA 总览、逐层证据、Raw 兜底、可复述结论。
5. **旁白母稿**：按镜头分段，技术名词保留原写法，不描述不可见思维链。
6. **字幕母稿**：一次只显示一个语义单位，常规一至两行；配音稿可以另存读音友好版本。
7. **原始画面**：当前视频基准为 1920×1080、对应 Harness 主题、完整三栏、无黑框、无烧录标注；旧版 2048×1056 素材只作为历史母稿继续复核。
8. **网页演示数据**：镜头时码、转场、字幕、聚焦框、标注卡、箭头路径、点击点和可选镜头运动。
9. **干净画面母版**：不含配音；发布版可以单独合成字幕与授权音轨。
10. **验收与来源记录**：产品 SHA、Source、素材文件、脱敏说明、逐帧结论、未覆盖风险。

十章之间的所有者审阅不再依靠聊天里手工维护链接。运行 `node scripts/generate-storyboard-review-index.mjs --require-videos` 会在 Git 忽略的 `tmp/storyboard-video/review-index.html` 生成统一审片首页：每章同时给出 HTML 动效模板、无字幕干净播放、本地 MP4、页内预览、中文事实章节、Source 边界和下一道门。页面只链接仓库相对路径，不复制视频、Capture 或本机绝对路径；历史试剪与正式母版分开展示。逐章结论与短备注只保存在当前浏览器，并按生成时的精确候选 SHA 隔离；所有者可显式导出一份 JSON 交接，但页面不上传数据，也不自动把 catalog 状态推进到下一阶段。

## 故事结构

每章默认使用六段结构；没有必要时不增加章节：

1. **提出误解或难题**：例如“Skill 是不是一整篇始终占用上下文的提示词？”
2. **给出无需背景知识的任务**：查看目录、读取公开 README、建立两项只读计划等。
3. **先看 PMA 总览**：让观众先知道完整闭环有几步，再进入细节。
4. **逐个打开证据**：每个镜头只证明一件事，并明确右栏由哪个点击动作打开。
5. **回到协议或 Raw**：对摘要有疑问时展示原始角色、顺序、ID 和字段路径。
6. **形成一句可复述结论**：观众能把 Harness、模型和工具的边界说清楚。

不为追求“丰富”加入需要额外业务知识的案例。复杂度应该来自 Agent 机制本身，而不是免邮规则、真实代码库或陌生领域背景。

## 发布会式视觉基线

标题卡与转场参考 [OpenAI DevDay](https://openai.com/devday/) 和 [Anthropic Code with Claude](https://www.anthropic.com/events/code-with-claude) 的公开发布会所体现的共同原则：一屏只讲一个观点、使用有舞台感的大字号排版、保留充足留白，并让真实产品演示成为主要证据。这里参考的是信息层级与节奏，不复制两家的 Logo、字体、专属图形或品牌资产。

- **共同叙事语法**：开场先提出一个具体问题，随后给出一句判断，再用真实 Viewer 证据证明；不把功能列表、长解释和结论同时塞进一张标题卡。
- **Codex 章节**：深石墨画布、近白正文和克制的 PMA 蓝色强调；采用严格左对齐网格和更直接的切换节奏，不使用渐变、玻璃效果或卡片堆叠。
- **Claude Code 章节**：暖纸色画布、深棕正文和低饱和陶土色强调；排版更舒展、停顿稍长，允许使用不承载信息的简单几何信号，但不能与标题或字幕争夺注意力。
- **跨 Harness 章节**：使用暖中性底色作为桥接，不把两套品牌色平均铺满一屏。
- **真实 Viewer 镜头**：始终完整占据 16:9 画布，不能为了“像 PPT”而缩进舞台框、增加黑边、电脑外壳或装饰背景。
- **文字层级**：标题卡只保留眉题、一个核心判断、最多四步的短流程和一行补充说明；长解释交给旁白与用户手册。
- **标题卡门禁**：`demo-storyboard-smoke.mjs` 会限制主题名称、标题长度、单行短标签和一至四个流程节点；协议差异等长解释不能塞入流程行，应留给旁白、正文镜头或页脚的一句边界说明。
- **动效节奏**：内容按眉题、标题、流程、补充说明分层进入；只使用缓慢淡入和小幅位移，不使用弹跳、旋转或无意义的连续运动。关键标题与复杂证据仍按实际阅读时间停留。

### 五种固定镜头语法

1. **问题封面**：只问一个观众立即能理解的问题，前 2 秒先让标题稳定出现，再开始解释。
2. **机制判断**：用一句话说清用户、Harness、模型或工具之间的关系；流程行只保留二至四个短节拍。
3. **真实证据**：Viewer 全幅出现，标注随旁白逐项进入；同一时刻只保留理解当前结论所必需的信号。
4. **必要对照**：只有在前后状态、两种协议或调用与结果必须同时比较时才并列；上一项先降权，下一项再出现。
5. **记忆点收束**：片尾只留一句可以复述的结论，以及最多四个用于回忆顺序的短词；不重新列一遍整章功能。

每一章不必机械包含五种镜头，但不得增加纯装饰页。判断一个镜头是否成立的标准是：关闭旁白后，观众仍能在三秒内说出这一屏希望他注意什么；如果说不出来，应删字、拆镜头或回到真实 Viewer 证据。

这套视觉语言必须在 1920×1080 主母版与 1024×576 紧凑审阅档同时通过：前者代表正常全屏浏览器，后者只用于暴露缩放、溢出和标注拥挤问题，不作为正式视频清晰度目标。

全局标题卡模板变化时，不必重新改写或重录 Viewer Source。先只重录所有 `source_image` 为空的稳定复核点，再用原有证据帧重建联系表：

```bash
node scripts/capture-storyboard-review-frames.mjs claude-planning \
  --card-scenes-only \
  --quality 70
```

这个局部模式会把同名旧 PNG 审阅代理迁移为 JPEG，并保留其他已验收证据帧；它不能跳过双尺寸联系表和逐张标题卡审视。由于正式 MP4 真实播放同一份 CSS，任何全局标题卡或转场变化都会使旧母版降为历史参考，必须等中文故事确认后重新导出。

## 网页标注与转场层

网页播放器是非破坏性合成层，不替代 Viewer，也不修改原始截图：

```text
真实 Viewer 原始帧
  + timeline.zh-CN.json（镜头、字幕、转场）
  + overlays（聚焦框、文字、箭头路径、点击点）
  = 可重复播放的 HTML 母稿
  → 浏览器录制 / FFmpeg
  → 剪映或其他编辑器添加授权配音与最后润色
```

初始实验入口为 `assets/demo/storyboard/index.html`。它必须支持：

- 16:9 播放画布、暖白背景和完整截图等比缩放，不用黑边框包装产品画面；
- 不经过黑场的慢速淡入淡出；
- 标注卡、聚焦框、SVG 折线箭头和点击波纹分别控制出现时机；
- 键盘前后翻页、暂停、进度条和 `?present=1` 无控件播放；
- 从同一审阅入口切换十个章节，并直接跳到时间线声明的稳定复核点；章节和复核点选择器只在制作模式出现，不能进入 `present=1` 画面母版；
- 制作模式显示当前演示对应的中文用户手册小节，审阅者可以从画面直接回到功能事实；该入口与其他控制器一样不得进入 `present=1`；
- 制作模式提供“章节审阅”面板，在一处显示目标问题、观众、Source 边界、当前状态、下一道确认门，以及旁白、字幕、manifest 和两档联系表；这些信息来自同一 catalog，不另建手工状态页；
- 画面、字幕和标注全部来自章节 JSON，以便翻译或界面更新时局部替换；
- `review=1` 只用于稳定审查帧：按 `at_ms` 冻结当时已经出现、弱化或退出的标注，停止画面淡入、镜头运动和点击波纹动画；正式播放不得携带该参数；
- `subtitles=0` 用于干净画面母版：只隐藏网页字幕层，不改变镜头、标注、点击波纹或转场；带字幕内部预览必须显式选择，不能覆盖干净母版；
- 未来可增加局部放大，但默认保持完整三栏，只有证据在全屏尺寸仍无法阅读时才启用。

统一章节清单保存在 `assets/demo/storyboard/catalog.zh-CN.json`。每项必须声明 `timeline`、`guide`、`guide_section` 与 `review`；`review` 固定包含问题、观众、Source 边界、发布状态、下一道确认门、可执行的 `story` 叙事合同、产品新鲜度边界，以及旁白、字幕、manifest、1920 联系表和 1024 联系表。文档映射只能指向纳入审计的中文公开文档和其中真实存在的标题，审阅资料必须真实存在且可进入 Git。新增、删除或重命名章节时必须同步清单；生产审计要求 catalog 与所有同时具有 manifest 和时间线的可发布章节完全一致。

`story` 不是自动评价文案“好不好听”，而是防止已经确认的叙事骨架在后续改版中静默丢失。每章必须声明：30 秒内结束的开场镜头及其旁白 / 字幕关键短语、60 秒内明确 PMA 价值的镜头、至少两个来自真实 Viewer 画面的证据镜头，以及最后一幕的可复述结论。`demo-production-audit.mjs` 会把这些引用与当前时间线逐项核对，同时检查 manifest 仍有观众、问题、结论和不讲范围；人工故事审阅仍是发布门，关键短语门禁不能替代人的理解。

时间线数据的最小检查：

```bash
node scripts/demo-storyboard-smoke.mjs assets/demo/source/claude-skill/video/timeline.zh-CN.json
```

切换章节时只替换时间线参数，例如子 Agent 章节：

```bash
node scripts/demo-storyboard-smoke.mjs assets/demo/source/claude-subagents/video/timeline.zh-CN.json
```

字幕时码由同一份时间线生成，避免镜头时长变化后手工维护两套事实：

```bash
node scripts/timeline-subtitles-to-srt.mjs \
  assets/demo/source/claude-planning/video/timeline.zh-CN.json \
  assets/demo/video/pma-claude-planning.zh-CN.srt
```

跨章节检查不能只相信目录名或 manifest 中的文字。下面的命令会核对时间线、旁白、SRT、Source 图片、双尺寸审阅图的真实像素、Git 可追踪性、`media-budget.json` 规定的体积与格式边界，以及常见隐私哨兵：

```bash
node scripts/demo-production-audit.mjs
```

已经声明 `review_points` 的章节可以单独使用严格模式，要求两个尺寸的文件名与时间线逐点一致：

```bash
node scripts/demo-production-audit.mjs --strict translation
```

双尺寸审阅帧应从 catalog 和时间线统一生成。下面的命令会自行启动环回服务器与一次性无痕 Chrome，冻结每个 `review_points` 时刻、输出 1920×1080 / 1024×576 JPEG、验证真实像素并重建联系表：

```bash
node scripts/capture-storyboard-review-frames.mjs codex-compact --quality 70
node scripts/demo-production-audit.mjs --strict codex-compact
```

审阅帧只是可重建代理图，原始 Source 才是像素事实。媒体预算接近上限的章节必须把实际 JPEG 质量写入 manifest，例如 Codex compact 与协议排错章使用 `--quality 70`；降低质量后仍需在 1024×576 原尺寸查看最密集的 Raw、协议字段、字幕和标题卡，不能只凭联系表判断可读性。

第一次尝试新镜头时使用 `--output-root tmp/<chapter>-review-candidate`，原尺寸和联系表检查通过后再写入 catalog 声明的正式目录。该脚本不删除失效旧帧；严格审计会把多余文件作为显式问题交给制作者判断，避免自动清理误删人工素材。

### 从网页时间线导出干净视频母版

逐帧审阅完成后，再录制真实网页播放，而不是从 review JPEG 反向拼接动画：

```bash
node scripts/export-storyboard-video.mjs claude-tool-loop
```

脚本按真实时间播放章节，使用 Chrome / Chromium / Edge 的 CDP 连续画面流和 FFmpeg 生成 1920×1080、30 fps、H.264 MP4。默认隐藏网页字幕且不创建音轨或字幕轨，后续由独立 SRT、授权配音和 `compose-demo-video.py` 生成语言版本。完整四分钟章节会按真实时长录制，不能为了加快生产而压缩关键阅读镜头。

第一次只录目标切片，确认转场和渐进标注以后再跑全章：

```bash
node scripts/export-storyboard-video.mjs quickstart \
  --start-seconds 78 \
  --duration-seconds 16 \
  --output tmp/storyboard-video/quickstart/system-sequence.mp4
```

输出旁边的 `.render.json` 是该次画面的交接证据。它记录精确 HEAD、工作区状态、源时间线、浏览器和 FFmpeg 版本、起止范围、编码帧数、是否显示字幕以及环回隐私边界。只有干净工作树上的整章无字幕导出才标记 `publishable_picture_master: true`；切片、脏工作树候选或带字幕预览都只能用于内部审阅。大体积 MP4 继续保存在 `tmp/`、Release 或对象存储，不进入主仓库。

多章母版导出或替换后，重新生成统一审片首页并要求所有正式母版合同通过：

```bash
node scripts/generate-storyboard-review-index.mjs --require-videos
```

默认入口是 `http://127.0.0.1:43115/tmp/storyboard-video/review-index.html`。页面中的“HTML 模板”用于逐句、逐标注审阅，“干净播放”用于检查正式画面层，“打开 MP4 / 页内播放”用于检查编码结果；三者不能互相替代。

看完一章后，在同一卡片选择“故事线通过 / 需要修改 / 暂缓决定”，短备注尽量写成可执行的镜头反馈，例如具体时码、目标证据与遮挡问题。顶部进度只统计已经作出结论的章节；备注本身不会把“未审阅”算成完成。页面把记录保存在按候选 SHA 命名的 `localStorage` 键中，导出的 `peekmyagent_storyboard_owner_review` JSON 同时携带精确 SHA、工作区是否干净、各章结论、备注和时间戳。“清空本轮记录”需要在十五秒内再次点击确认，避免系统弹窗打断审片或单击误删。导出是用户主动动作，不代表发布批准；分享前先检查备注是否含真实提示词、源码、路径或密钥，再由维护者根据所有者确认手工更新 catalog。

维护者收到 JSON 后按以下顺序处理，不能跳过候选提交检查：

```bash
node scripts/storyboard-review-handoff.mjs \
  --input tmp/storyboard-review/review.json \
  --expected-target <完整的四十位候选提交> \
  --check

node scripts/storyboard-review-handoff.mjs \
  --input tmp/storyboard-review/review.json \
  --expected-target <完整的四十位候选提交> \
  --output tmp/storyboard-review/summary.md
```

第一条只验证 schema、当前十章清单、计数、UTC 时间戳、候选 commit 是否在本地可解析，以及备注中常见的凭据和隐私路径哨兵；失败消息不会回显命中的值。第二条生成不含备注原文的安全摘要。确需查看原文时显式增加 `--show-notes`，并把输出留在 `tmp/`；随后仍要人工脱敏。存在“需要修改”时，只改对应章和镜头，生成新 SHA 后重新审阅；所有章节都通过也只代表故事结论已收齐，catalog 的 `ready-for-voice` 仍由维护者人工推进。

生成成功仍不能代替观看。每章至少抽查：第一帧、每次场景转场前后、每个编号新增前后、旧编号降权或退出后的稳定帧、字幕安全区和末帧；确认没有黑边、浏览器控制器、提前出现的编号、空白帧、字幕大黑框或敏感内容。

如果只需要从已经复核的帧重建联系表，继续使用统一联系表脚本；不能用一张缩略联系表反向证明原始帧尺寸：

```bash
python3 scripts/build-demo-contact-sheet.py \
  assets/demo/source/claude-planning/recording/review-1920 \
  assets/demo/source/claude-planning/recording/review-1920/contact-sheet.jpg
```

### 箭头草稿字段

每条箭头在写入 JSON 前先回答四个问题，并保存在 `draft` 字段中：

1. 起点为什么放在这块留白？
2. 终点具体落在哪个控件或字段的哪一侧？
3. 路径避开了哪些可读内容？
4. 这条箭头唯一要证明什么？

没有草稿说明的箭头不得进入正式时间线。生成成功也不等于验收通过；必须按原尺寸和约 1024px 预览真实查看。

### 标注的出现顺序

标注按 PPT 的讲解节奏出现，不是进入镜头后一次性铺满：

- `delay_ms` 决定标注何时出现；可选 `end_ms` 决定何时淡出；需要保留旧重点但降低视觉权重时使用 `dim_ms`；
- 编号表示讲解的时间顺序，不是画面元素清单；同一镜头即使最终要出现 1、2、3、4，也不得在镜头进入时一次性铺满；
- 第一个状态必须只出现编号 1；旁白完成当前重点以后，才进入含编号 2 的下一个状态。相邻编号至少间隔 2.5 秒，复杂证据应更慢，不能为了赶时长压缩讲解；
- “点击来源 → 查看证据”通常先出现 1，讲完后让 1 淡出，再出现 2；两者可以有约 0.4～0.7 秒交叉，交接完成后画面只留下当前重点；
- 需要同时比较、建立因果或说明位置映射的关系，例如“父级调用 #1 → 结果回流 #5”，可以让 1 保留，再出现 2；此时旧标注应通过 `dim_ms` 降为次要视觉层级，不能与当前编号争夺注意力；
- 同一画面的 1、2、3、4 必须分别拥有出现时刻。不得仅为了最终截一张“全标注图”而让它们同时弹出；是否保留旧编号取决于讲解关系，而不是编号数量；
- 每次增加下一个编号，都要在镜头草稿中说明前一个编号是继续保留、交叉淡出还是完全替换，以及这个决定服务于哪一种因果或对照关系；
- 同一画面允许使用 1、2、3、4 和短文字，只要它们表达明确阅读顺序，而不是为了填满空白；
- 单一重点可以只用点击波纹或轻描边，不强制编号和说明卡；
- 圆形编号内使用普通数字，由容器负责居中，不再嵌套 `①` 一类自带圆圈的字符。

箭头使用细线和开放式箭头头部。优先使用一段短直线；确有跨区关系时最多使用一个有意义的转折。终点落在控件或聚焦框边缘并留出呼吸，不落在文字中央，也不追随原生小箭头绕出钩形路线。仅靠编号位置和聚焦框已经能建立关系时，不再加箭头。

## 每章完成门

- 前 30 秒内，目标用户不需要项目背景就能理解问题和任务；前 60 秒内必须明确 PMA 在本章怎样把黑盒行为变成可检查证据；
- 每个产品结论都有一个可点击 Viewer 证据，重要结论另有协议或 Raw 兜底；
- 合成轨迹只证明产品展示能力，涉及当前 Harness 实现的结论已经真实 CLI 交叉核对；
- 关键阅读镜头通常保留 15～26 秒，普通镜头不少于 8 秒；
- 字幕一次一个语义单位，稳定底部居中；标注不承担整段字幕功能；
- 箭头终点准确，线路沿留白，文字和编号视觉居中；
- 1920×1080 原图与 1024×576 预览中的每个时间线复核点均人工检查；旧版 2048×1056 原图保留时也必须单独核对；
- Source、系统提示、路径、模型回复和工具结果全部可公开、可重建；
- 中文事实冻结后再翻译，其他语言不反向改变中文教学结构。

## 功能更新后的主动触发

功能到文档的影响映射仍以[用户文档与演示素材持续更新机制](documentation-maintenance.md)为准。catalog 中每章的 `review.freshness.product_impact_ids` 声明它实际依赖哪些产品边界；影响报告据此输出精确的 `required_demo_chapters`，不再只写“可能需要更新某类演示”。

收到功能更新后先运行：

```bash
node scripts/demo-freshness-audit.mjs --target HEAD
node scripts/demo-freshness-audit.mjs --target HEAD --chapter quickstart --json
```

报告分别回答三个问题：manifest 记录的产品证据 SHA 之后，本章关注的运行时代码是否变化；确定性 Source 生成脚本更新后，Source 图片与 manifest 是否重建；共享播放器、时间线或 Source 图片更新后，已提交双尺寸复核帧是否重生成。第一项要求重新检查真实 Harness / Viewer，第二项要求用非敏感场景重建 Source，第三项只要求重渲染；任何一项都不能代替另外两项。完成对应更新和逐帧审视后，再以 `--strict` 验证选中的章节。

产品所有者主工作区的 heartbeat 会在 `origin/main` 变化后生成携带精确 SHA、受影响章节、产品证据状态、Source 生成脚本状态和复核帧状态的文档任务；它不能跳过真实页面复核，也不能自动发布未经审视的截图。共享 GitHub 工作流继续只生成只读 Job Summary，不会因克隆仓库而自动创建本地调度。
